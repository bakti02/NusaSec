# NusaSec Core → UI Integration Map

This document is the frontend contract derived from the supplied `nusasec-core` source. The frontend must not invent customer-security endpoints.

## Canonical customer endpoints

| UX surface | Core endpoint | Purpose |
|---|---|---|
| Control Tower | `GET /api/v1/dashboard/overview` | Canonical overview: assets, risk, posture, identity graph, crypto, compliance, CBOM, PQC |
| Asset inventory | `GET /api/v1/product/assets` | Tenant-scoped assets |
| Asset dossier | `GET /api/v1/product/assets/{asset_id}/dossier` | Asset context, business context, findings, related assets, scan timeline |
| External exposure | `GET /api/v1/product/external-exposure` | Internet-facing/public exposure |
| Risk | `GET /api/v1/product/top-risks` | Prioritized risks |
| Attack paths | `GET /api/v1/product/attack-paths` | Risk graph / attack-path context |
| Identity | `GET /api/v1/product/identities` | Identity explorer |
| Configuration change | `GET /api/v1/product/diffs` | Compare latest scans |
| Coverage | `GET /api/v1/product/coverage` | Telemetry coverage, freshness, confidence |
| Work | `GET /api/v1/product/my-work` | Current principal's remediation work |
| Remediation | `GET /api/v1/product/remediation` | Remediation task list |
| Risk exceptions | `GET /api/v1/product/risk-exceptions` | Risk acceptance/exception workflow |

## Important constraints

- `Threat Intelligence` is not exposed as a standalone customer GET endpoint in the supplied Core API. The current UI therefore labels the workspace **Risk & Threat Intelligence** and uses the Core's attack-path intelligence rather than fabricating IOC/campaign data.
- `Incident` currently exposes POST creation and status-transition endpoints under `/api/v1/reliability/incidents`; the supplied Core does not expose a customer GET incident-list endpoint. The UI therefore supports creation but explicitly states the read-side limitation.
- Compliance has evaluation and regulatory applicability APIs; the frontend must not invent `/api/v1/compliance` GET routes.
- All API calls pass through the configurable frontend API base. Same-origin deployment uses an empty base; separate static hosting can set `window.NUSASEC_API_BASE` or `localStorage.nusasec_api_base`.
- No security metrics are fabricated when Core data is unavailable.

## UX model

The Core's customer security experience is represented as:

**Discover → Understand → Prioritize → Investigate → Act → Verify → Prove**

The UI should therefore use entities and context rather than isolated KPI cards.

## Product architecture observed in Core

The supplied Core contains customer capabilities including multi-cloud discovery, risk/graph analysis, security posture, identity, CBOM/crypto posture, PQC, regulatory/compliance, Secure Web, incident/reliability, reporting/documents, integrations and commercial/product catalog services.

The frontend should expose these as coherent workspaces/products, not as a flat list of invented "engines".
